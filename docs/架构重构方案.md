## 0. 一句话结论

**你已经在用 SQL 了，但只用了一半。** `kb/kb.db` 装下了整个知识库（7579 个 KU、35529 条链接），
但题库、闪卡、大纲、成绩全在 JSON 文件里，两套体系靠人手搬运。
"每次加一点东西都很慢"不是因为没用数据库，而是因为**真源被切成了两半**。

本方案的核心动作不是"改用 SQL"，而是：

> **把 SQL 从「知识库存储」升级为「唯一真源」，让 JSON 从「手工维护的源」降级为「从库里导出的产物」。**

**前端一行都不用改。** 现在纯静态读 JSON 是优点（部署简单、离线可用、你手动上线方便），全部保留。

## 2. "慢"的四个根因

### 根因 1：数据三副本，靠手工同步

改一个题库 → 要写 `public/data/`（前端）+ `rules/`（后端），漏一处就前后端不一致。
2026-08-12 就实际发生过：前端有 18 库，后端只看到 10 库；前端 16 套闪卡，后端只有 1 套。

### 根因 2：题目与知识库脱钩 ← **这是你说的核心痛点**

> "做功能时，知识库需要补一部分内容，速度就很慢。"

根因在此：**题目不在库里，也不挂 `ku_id`。**

所以你**没法用一句 SQL 问出"这个大纲考点下还缺几道题"**，只能：
人工翻 KU → 人工判断哪里缺 → 人工写题 → 人工塞 JSON → 人工同步两处。

这个链条上每一步都是手工的，所以补内容必然慢。

### 根因 3：43 个零散脚本，没有流水线

加一份新资料要凭记忆按顺序手跑：
`OCR → _build_kb → build_links → 生成题库 → 生成闪卡 → 同步 rules/materials`

任一步静默失败就断链。这几天踩的坑全是这个模式的必然产物：

- `--ku` 被 argparse `allow_abbrev` 当成 `--ku-mode` 前缀缩写吞掉参数 → 落库崩了，但没人发现，`kb.db` 一整天没动
- 收尾脚本硬编码等待 PID `29936`，实际进程是 `32640` → 误判 + build 失败后不拦截，继续跑了后续步骤
- watchdog 用 `wmic`（本机已禁用）→ `find_main_pid()` 恒返回 None → 反复误拉起，最终 22 个进程死锁风暴
- doc2kb 整本模式在末尾才一次性写 JSON → 中途崩溃，514 页 OCR 全部丢失

**这四个 bug 的共性**：没有统一流水线 + 失败不阻断 + 无中间落盘。

### 根因 4：每次全量重链

`build_links.py` 加一本书就重算全部 35529 条链接。

### 补充：SQL 治不了的部分（诚实说明）

教材 OCR 那 1 小时是 **docling 处理 514 页扫描件的固有耗时**，和数据库无关，改架构也快不了。
这部分只能靠"分页落盘 + 断点续跑"（已在 `kb/ocr_textbook_pages.py` 实现）来保证不白跑，
而不能靠重构变快。

## 3. 目标架构

### 3.1 数据流（单向，唯一真源）

```
                    ┌──────────────────────────────┐
   PDF / 资料  ──►  │  OCR (doc2kb, 分页落盘)       │
                    └──────────────┬───────────────┘
                                   ▼
                    ┌──────────────────────────────┐
                    │   kb.db  ★唯一真源★          │
                    │                              │
                    │  现有：documents / sections   │
                    │        knowledge_units       │
                    │        ku_links / pages      │
                    │        product_special       │
                    │                              │
                    │  新增：questions ──► ku_id    │
                    │        flashcards ──► ku_id  │
                    │        syllabus              │
                    │        banks (题库定义)       │
                    └──────────────┬───────────────┘
                                   │  一条命令导出（幂等）
                                   ▼
                    ┌──────────────────────────────┐
                    │  public/data/*.json  (生成物) │
                    └──────────────┬───────────────┘
                                   │  自动同步
                                   ▼
                    ┌──────────────────────────────┐
                    │  rules/ + materials/ (生成物) │
                    └──────────────────────────────┘
                                   │
                                   ▼
                         server.py (薄壳，零改动)
                                   │
                                   ▼
                         前端 SPA (零改动)
```

**关键约束**：
- `public/data/`、`rules/`、`materials/` 全部标记为**生成物**，不再手工编辑
- 所有内容变更只发生在 `kb.db`
- 导出必须**幂等**：同样的库导出两次，文件字节一致（便于 diff 和放心部署）

### 3.2 新增表设计

```sql
-- 题库定义
CREATE TABLE banks (
    id            TEXT PRIMARY KEY,      -- 'gbt_2951_full'
    name          TEXT NOT NULL,         -- 'GB/T 2951 全系卷'
    bank_version  TEXT DEFAULT 'bank/2.0',
    standards     TEXT,                  -- JSON 数组
    trust_level   TEXT DEFAULT 'verified', -- 'verified' | 'online_unverified'
    scoring       TEXT,                  -- JSON
    source_note   TEXT,
    created_at    TEXT DEFAULT (datetime('now'))
);

-- 题目（核心新增）
CREATE TABLE questions (
    id          TEXT PRIMARY KEY,        -- 'C001' / 'TJ_C041'
    bank_id     TEXT NOT NULL REFERENCES banks(id),
    qtype       TEXT NOT NULL,           -- choice|judge|fill|calc|essay
    stem        TEXT NOT NULL,           -- 原 q 字段
    options     TEXT,                    -- JSON 数组（选择题）
    answer      TEXT,                    -- 标量或 JSON；NULL = 答案待核
    subs        TEXT,                    -- JSON: [[label,target,tol,pts],...] 计算题
    points      REAL DEFAULT 1,
    explain     TEXT,
    src         TEXT,                    -- 'GB/T 2951.13-2008 8.1'  ← 挂载桥梁
    ku_id       INTEGER REFERENCES knowledge_units(id),   -- ★ 关键关联
    section_id  INTEGER REFERENCES sections(id),
    difficulty  INTEGER,                 -- 1-5，可选
    answer_state TEXT DEFAULT 'ok',      -- ok | pending_review（网上题库）
    created_at  TEXT DEFAULT (datetime('now'))
);
CREATE INDEX idx_q_bank  ON questions(bank_id);
CREATE INDEX idx_q_ku    ON questions(ku_id);
CREATE INDEX idx_q_type  ON questions(qtype);

-- 闪卡
CREATE TABLE flashcards (
    id         TEXT PRIMARY KEY,
    deck_id    TEXT NOT NULL,
    front      TEXT NOT NULL,
    back       TEXT NOT NULL,
    std        TEXT,
    method     TEXT,
    priority   INTEGER,
    src        TEXT,
    ku_id      INTEGER REFERENCES knowledge_units(id)     -- ★ 同样挂 KU
);
CREATE INDEX idx_fc_deck ON flashcards(deck_id);
CREATE INDEX idx_fc_ku   ON flashcards(ku_id);

-- 考试大纲（现 syllabus_2026.json 的 125 个 items）
CREATE TABLE syllabus (
    id              TEXT PRIMARY KEY,    -- 'S001' ...
    part            TEXT,                -- 'resource' ...
    category        TEXT,                -- '教材章节' ...
    sub_no          TEXT,
    topic           TEXT NOT NULL,
    requirement     TEXT,
    cognitive_level TEXT,                -- 了解|熟悉|掌握|熟练掌握
    ref_standards   TEXT                 -- JSON 数组
);
```

### 3.3 题目如何挂到 KU 上（技术可行性已验证）

题目的 `src` 字段天然带"标准号 + 条款号"：

```
questions.src = "GB/T 2951.13-2008 8.1"
                 └──── 标准号 ────┘ └条款┘
                        │             │
                        ▼             ▼
        documents.title 匹配    sections.clause_no 匹配
                        └──────┬──────┘
                               ▼
                          sections.id
                               ▼
                    knowledge_units.section_id
                               ▼
                       questions.ku_id  ✅
```

这条路径是**现成可用的**——不需要人工标注，一次性回填脚本即可完成 765 道题的挂载。
挂不上的（`src` 为空或标准未入库）标记 `ku_id = NULL`，作为待补清单单独输出。

### 3.4 CLI：把 43 个脚本收敛成一个入口

```bash
# 加一份新资料（全自动，失败即停）
python kb/pipeline.py add <pdf>
#   → OCR(分页落盘/断点续跑) → 落库 → 增量重链 → 导出 JSON → 同步 rules/materials

# 只重新导出（改了库里内容后）
python kb/pipeline.py export

# ★ 直接治痛点：列出缺题的考点
python kb/pipeline.py gaps --syllabus S004
python kb/pipeline.py gaps --min-questions 3      # 全局：题目数<3 的考点

# 体检
python kb/pipeline.py doctor
#   → 副本一致性 / 孤儿 KU / 答案缺失 / 挂不上 KU 的题目
```

#### `gaps` 命令的实现（一句 SQL 就够）

这正是当前架构做不到、重构后立刻能做到的事：

```sql
-- 某大纲考点下，有 KU 但题目不足的知识点
SELECT ku.id, ku.title,
       COUNT(q.id) AS n_questions
FROM knowledge_units ku
JOIN ku_links kl ON kl.ku_id = ku.id
LEFT JOIN questions q ON q.ku_id = ku.id
WHERE kl.syllabus_id = 'S004'
  AND ku.is_exam_point = 1
GROUP BY ku.id
HAVING n_questions < 3
ORDER BY n_questions ASC;
```

→ 输出直接就是"该出题的清单"，按缺口排序。
你要补内容时不再人工翻，而是照单出题。

## 4. 迁移步骤（分 5 步，每步可独立验证 / 回滚）

| # | 步骤 | 产出 | 验证方式 | 风险 |
|---|---|---|---|---|
| 1 | **备份 + 建表** | `kb.db` 新增 4 表（不动现有表） | 现有功能全跑一遍无变化 | 极低（纯新增） |
| 2 | **导入现有数据** | 765 题 / 17 套闪卡 / 125 考点入库 | 计数比对：库内数 == JSON 内数 | 低（只读 JSON） |
| 3 | **回填 `ku_id`** | 题目挂上 KU，输出挂不上的清单 | 挂载率报告 + 抽样人工核对 | 低（可重跑） |
| 4 | **写导出器** | `pipeline.py export` | **字节级 diff**：导出结果与现有 JSON 一致 | **中（关键闸门）** |
| 5 | **切换真源** | `public/data` 等标记为生成物 | 全量 HTTP 冒烟 + 线上部署验证 | 中 |

### 第 4 步是关键闸门

导出器写好后，先**不覆盖**现有文件，而是导到 `_gen/` 目录做逐字节 diff：

```bash
python kb/pipeline.py export --to _gen/ --dry
diff -r public/data/ _gen/
```

**只有 diff 为空（或差异全部可解释）才允许切换真源。**
这一步保证重构不改变任何线上行为——这是整个方案能安全落地的前提。

### 回滚策略

- 每步前 `kb.db` 打快照：`kb/_bak/kb.db.<步骤>.<时间戳>`
- `public/data/`、`rules/`、`materials/` 在第 5 步前整体备份到 `_bak/`
- 新增表不影响现有查询，任何一步失败可直接丢弃新表回到当前状态
- `server.py` 在整个过程中**零改动**，所以线上行为始终可预测

## 6. 明确不做的事（避免过度设计）

- ❌ **不引入 PostgreSQL / MySQL**。SQLite 完全够用：单机、单写入者、50 MB、只读查询为主。换重型数据库只增加部署负担。
- ❌ **不改前端**。静态读 JSON 是优点，保留。
- ❌ **不让前端直连数据库**。会破坏"手动部署一个静态站"的简单性。
- ❌ **不改 `server.py` 的薄壳设计**（其 L12-17 自述的架构红线）。它继续只读 `rules/` 和 `materials/`。
- ❌ **不做 ORM**。原生 `sqlite3` + 几个查询函数足够，引入 SQLAlchemy 是负担。
- ❌ **不重写 OCR 环节**。`ocr_textbook_pages.py` 的分页落盘 + 断点续跑 + 单实例锁已经是正确解法，直接纳入流水线。
